## 0. 已锁定决策清单（不再讨论，直接执行）

| # | 决策项 | 结论 |

## 1. 背景与目标

### 1.1 一期现状（代码审计结论）

一期 MVP 已实现：手机号登录（固定验证码）、单次打卡、请假申请与审批、AI 合规校验建议、自然语言排班（LLM 解析软约束 → OR-Tools CP-SAT 求解 → LLM 解释）、RAG 规则问答助手、AiInteractionLog 埋点闭环。架构分层正确（预测层 / 优化引擎层 / LLM 交互层 / 应用数据层），核心红线（排班绝不由 LLM 计算、AI 不自动审批）已落实。

一期遗留缺陷（本期必须修复，详见 §9 Sprint 1）：

1. 埋点记录的是「配置的模型名」而非「实际调用的 Provider/模型」——mock 降级时日志仍写 claude-*，数据失真
2. 「AI 智能排班」按钮无防抖，实测出现 1 秒间隔 8 连击
3. 排班保存 `source=ai_generated` 回填链路存在矛盾（35 条排班全部为 manual，与采纳日志冲突）
4. 请假批准后不扣减假期余额
5. `lastWeekHours` seed 写死，公平性软约束形同虚设
6. 只有签到无签退，真实工时不可算

### 1.2 二期目标

以经授权旧版视觉参考为需求输入，将其移动端功能全部迁移至 Web 端，交付一个可完整演示「配置 → 预测 → 智能排班 → 打卡考勤 → 异常处理 → 换班 → 报表 → AI 反馈度量」全链路的试点级系统。

**北极星指标**：AI 排班推荐采纳率（周）≥ 75%，采纳后平均编辑距离 ≤ 8%。

## 3. 功能需求

### 3.1 门店配置模块（manager/admin）

**3.1.1 V2S 配置**：按星期几（周一~周日）设置 V2S 下限与上限（V2S = 每班次客流 ÷ 在岗人数）。默认 seed：下限 30，上限 60，周末下限 40 上限 80。

**3.1.2 最低人力配置**：按（星期几 × 班次 × 岗位）设置最低在岗人数。默认 seed：收银每班次 1 人；销售早/午 2 人、晚 2 人，周末各 +1。

**3.1.3 门店活动日历**：日历视图，为具体日期打标签（`promo` 促销 ×1.3 / `new_arrival` 上新 ×1.15 / `holiday` 节假日 ×1.4），支持月/年视图切换。标签系数进入客流预测（§4）。

**3.1.4 员工管理**：列表展示岗位、入职日期、新老标识、销售能力、绩效档位、综合分、本周工时；店长可编辑岗位与能力标签。

**3.1.5 营业状态**：仅保留「当日是否营业」开关（班次时间已由 D2 锁死，不提供编辑）。

### 3.2 排班四步向导（manager）——本期核心重构

替换一期的「一键生成」，路径：排班管理 → 选择计划周 → 进入向导。

**Step 1 排班准备**
- 选择排班模式：`做五休二`（每人每周工作天数 ≤5）或 `做六休一`（≤6），作用于全店本计划周
- 展示并确认本周营业状态（读 3.1.5）
- 展示员工「不可供班」时段列表（员工端提交，见 3.5.3），店长可代为增删

**Step 2 业务预测**
- 系统按 §4 算法自动生成本周每日每班次客流预测，图表展示（预测值 vs 近 4 周均值）
- 店长可逐格调整预测值，调整必须填写原因（落库 `adjustReason`）
- 支持录入每日营业额目标（仅展示用，不进算法）

**Step 3 人力预测**
- 系统按 §4.3 公式将客流折算为（日 × 班次 × 岗位）所需人数，**只读**；不满意需返回 Step 2 调客流（对齐手册交互）
- 展示折算依据：客流值、V2S 区间、最低人力兜底

**Step 4 自动排班**
- 可选输入自然语言诉求（LLM 解析为软约束，一期能力保留）
- 点击「自动推荐」→ 引擎求解（§5）→ 网格展示班表 + 缺口提示 + AI 自然语言解释 + **全天综合平均分**指标行
- 单元格编辑：点击格子增删班次、右键复制/粘贴/清空该员工该日
- 工具操作：`清空排班`（二次确认）、`恢复推荐`（回到引擎原始方案）、`复制历史`（按天复制过往某日班表）、`导出 Excel`
- 「发布」→ 班表落库生效，全体员工可见；同时按 §8 回填采纳与编辑距离埋点

### 3.3 打卡与考勤（D7 + D8 简化版）

**3.3.1 动态码机制**
- 码 = 6 位数字，`HMAC(storeId, floor(now/60s), serverSecret)` 派生，**无需建表**，服务端无状态校验
- 校验窗口：当前 60s 窗口 + 上一窗口（容忍时钟偏移与输入耗时）
- 展示页：`/clock-code`（manager 登录后访问），大字号展示 + 60s 倒计时自动刷新，供门店前台电脑常开
- 员工打卡页：选择签到/签退 → 输入 6 位码 → 校验通过记录时间戳；错误码提示「动态码无效或已过期」

**3.3.2 签到/签退与异常判定**（查询时实时计算，不预生成异常表）
- 签到有效窗口：班次开始前 2h ~ 开始后 2h；签退有效窗口：班次结束前 2h ~ 结束后 4h（对齐手册「向前 4 小时向后 6 小时」思路的简化）
- 异常类型：`late` 迟到（首次有效签到 > 班次开始）、`early_leave` 早退（末次有效签退 < 班次结束）、`missing_in` / `missing_out` 缺卡
- 实际出勤工时 = 班次时段 ∩ [签到, 签退]（对齐手册定义）
- 未排班日打卡：记录但标记 `unscheduled`，不计工时

**3.3.3 补卡流程**：员工提交（日期 / 签到或签退 / 补卡时间 / 原因）→ 店长审批 → 通过后生成校正记录，参与工时与异常重算。补卡单进入统一审批中心。

**3.3.4 考勤异常页（manager）**：按日期范围 / 员工 / 异常类型筛选，逐条展示异常明细；店长可从异常行直接发起「代提交补卡/请假」（对齐手册「异常处理」通道）。

### 3.4 审批中心（manager）

- 聚合三类单据：请假、补卡、换班；Tab 切换 + 状态筛选（待审批/已通过/已驳回）
- **批量操作**：勾选多条同类单据 → 批量通过 / 批量驳回（对齐手册）
- 审批记录页：全量历史可查
- 每类单据保留「运行 AI 合规校验」按钮（DeepSeek，建议仅供参考，人工终审）；**请假批准时同步扣减对应假期余额**（修复一期缺陷）

### 3.5 员工自助（employee）

- **3.5.1 换班**（D9）：选择本人某未来班次 → 选择同店**同岗位**候选员工（系统自动过滤：候选人该时段无班、换入后不违反 §5 全部硬约束）→ 候选人确认 → 引擎校验 + AI 合规建议 → 店长终审 → 双方班表原子互换，记录 `source=swap`
- **3.5.2 请假**：沿用一期（年假/病假、全天/时段），批准后扣余额
- **3.5.3 不可供班登记**：轻量声明「某日某班次不可上班」（如学生兼职课程时间），不占假期余额，进入引擎硬约束；店长在排班 Step 1 可见可改
- **3.5.4 AI 助手**：沿用一期 RAG 问答 + 页面导航，规则库按 §7.3 扩容

### 3.6 报表模块

| 报表 | 内容 | 可见角色 |
|---|---|---|
| 工时表 Monthly | 每员工每月：应出勤工时 / 实际出勤工时 / 迟到早退缺卡次数 / 请假小时 | manager（本店）、admin（全店） |
| 周工时分布 | 本周每员工排班工时柱状图，标注 40h 上限线 | manager |
| 周班次分布 | 每日每班次每岗位在岗人数 vs 需求人数（缺口标红） | manager |
| 全天综合平均分 | 本周每日综合能力平均分折线（对齐手册搭班指标） | manager |
| AI 指标看板 | §8 全部指标的周趋势 | manager（本店）、admin（全局） |

## 4. 预测层规格（客流仿真 → 预测 → 人力折算）

### 4.1 历史客流仿真（seed 阶段生成 8 周数据）

```
visitors(store, date, shift) = base(store) × dow(date) × shiftFactor(shift) × event(store,date) × N(1, 0.1)
```
- `base(store)`：每店基线客流 80–150（按店铺规模随机）
- `dow`：周一~周四 1.0，周五 1.2，周六/周日 1.5
- `shiftFactor`：早班 0.8，午班 1.2，晚班 1.0
- `event`：读活动日历标签系数（promo 1.3 / new_arrival 1.15 / holiday 1.4），无标签为 1.0
- 噪声：均值 1、标准差 0.1 的正态

### 4.2 预测算法（可解释的基线模型，预留 ML 接口）

```
forecast(d, s) = [0.6 × mean(近4周同星期几同班次) + 0.4 × 上周同星期几同班次] × event(d)
```
接口保持一期的 `getDemandForecast()` 抽象；TODO 标注后续可替换为时序模型。

### 4.3 人力折算（Step 3 公式）

```
总人力(d,s)   = clamp( ceil(forecast(d,s) / v2sUpper(dow)),
                       下界 = Σ最低人力(dow,s,*),
                       上界 = ceil(forecast(d,s) / v2sLower(dow)) )
收银需求(d,s) = 最低人力(dow, s, cashier)          // 收银按最低配置固定
销售需求(d,s) = max( 最低人力(dow, s, sales), 总人力 − 收银需求 )
```

## 5. 优化引擎 v2 约束规格（CP-SAT）

决策变量：`x[e, d, s] ∈ {0,1}`，e ∈ 本店收银+销售员工（店长不入集合，D4）。

### 5.1 硬约束

| # | 约束 | 实现 |
|---|---|---|
| H1 | 请假 / 不可供班时段不排 | 变量置 0 |
| H2 | 周工时 ≤ 40h（= ≤10 个班次） | Σx ≤ 10 |
| H3 | 班次间隔 ≥ 4h（D3） | 同日「早+午」「午+晚」互斥（间隔 0）；「早+晚」允许（间隔 4h）；跨日晚→早间隔 12h 天然合规，无需约束 |
| H4 | 排班模式：做五休二 ≤5 天 / 做六休一 ≤6 天 | 引入 `worked[e,d] = OR(x[e,d,*])`，Σworked ≤ N |
| H5 | 岗位严格匹配 | 收银需求仅由 cashier 满足，销售需求仅由 sales 满足（需求按岗位分列，见 §4.3） |
| H6 | 新老搭班：任何有人在岗的班次不能只有新员工 | 对每个新员工 e_j：`x[e_j,d,s] ≤ Σ x[e_senior,d,s]`（收银+销售的资深员工均可作为「资深在岗」） |

### 5.2 软约束（词典序权重，从高到低）

| # | 目标 | 权重 |
|---|---|---|
| S1 | 人数缺口最小化（按岗位维度，缺口变量吸收，返回 gaps） | 10000 |
| S2 | LLM 解析的店长自然语言偏好 | 200 |
| S3 | 岗位班次偏好（学习上月：统计各岗位上月各班次频次，频次最高班次作为该岗位偏好，P1 功能） | 50 |
| S4 | 综合能力均衡：最小化 Σ_d \|当日综合分总和 − 周日均值\|（线性化绝对偏差） | 10 |
| S5 | 公平性：上周工时高者本周少排（沿用一期，`lastWeekHours` 改为从上周已发布班表真实回算） | 1 |

### 5.3 输出

沿用一期结构：`assignments[] + gaps[] + status`，新增 `dailyAbilityScore[]`（每日综合分，供前端指标行与解释 prompt 使用）。

### 5.4 换班校验复用

换班请求（3.5.1）调用引擎轻量接口 `POST /validate-swap`：将互换后的两人班表代入 H2/H3/H4/H6 校验，返回 `valid + violations[]`。

## 8. AI 效果度量（B 档基线，D11）

| 指标 | 定义 | 目标 | 触发动作 |
|---|---|---|---|
| 排班推荐采纳率 | 发布的 AI 推荐 ÷ 生成总次数（周） | ≥ 75% | 连续 2 周低于目标 → 迭代 prompt（补 few-shot 失败案例）；低于 60% → 升级模型或加校验层 |
| 采纳后修改率 | editRatio > 0 的采纳占比 | ≤ 25% | 同上 |
| 平均编辑距离 | 采纳方案平均 editRatio | ≤ 8% | 分析高频改动格子模式 → 转化为新软约束 |
| 解析准确率 | 人工抽检 JSON 员工/班次映射正确率 | ≥ 92% | 低于 77% → 换模型 |
| 合规建议一致率 | AI 建议与店长最终决定一致（请假+补卡+换班） | ≥ 90% | 低于 75% → 换模型 |

**埋点修复三件套（Sprint 1 强制项）**：记录实际 provider/model；前端所有 AI 按钮加防抖 + loading 锁；`source=ai_generated` 回填链路修复。编辑距离在「发布」动作中计算：diff 引擎原始推荐 vs 最终发布班表，按（员工×日期×班次）格子计数。
